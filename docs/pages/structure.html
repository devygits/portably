How it works

Project structure

Every Portably project has the same files, the same page skeleton and the same three kinds of class name.

Files

site/
├── index.html              the first page
├── pages/                  more pages, only when the design has them
├── foundation/             Portably's shared CSS, never edited
├── tokens/
│   ├── tokens.json         the design system
│   └── tokens.css          generated by check
├── css/
│   ├── project.css         imports the four files below, in order
│   ├── base.css            project-wide element defaults
│   ├── layout.css          the page anatomy and shared layouts
│   ├── components.css      imports css/components/*.css
│   ├── components/         one recurring concept per file
│   ├── pages.css           imports css/pages/*.css
│   └── pages/              compositions for one page
├── js/main.js              behaviour, on data-js hooks
├── assets/                 images, icons, fonts
├── AGENTS.md               how to work on the project
├── DESIGN-SYSTEM.md        generated by check
├── DESIGN-SYSTEM.html      generated by check
├── portably.config.json    version, namespace, design context, decisions
└── README.md               pages, remote dependencies, known gaps

Every page loads foundation/system.css, tokens/tokens.css and css/project.css, in that order, and has the class pbly on <body>.

Page anatomy

Pages share one skeleton with the same names everywhere. Site pages stack sections; each section pads its content and holds one wrapper that sets the content width:

<section class="section pricing">
  <div class="wrapper">
    <header class="section-header">
      <p class="eyebrow">Pricing</p>
      <h2 class="section-header__title">Plans for every team</h2>
      <p class="section-header__intro">Start free and upgrade when you need to.</p>
    </header>
    <div class="pricing__plans">…</div>
  </div>
</section>

Application screens such as dashboards use the app shell: app-shell with app-shell__sidebar, app-shell__topbar and app-shell__main, and a panel for each region.

The values come from tokens, so the design changes how the skeleton looks, never what it is called.

Other layouts, such as documentation with a sidebar and a list of contents, keep wrapper for their width and define the layout in css/layout.css under a project name. This site uses docs-layout.

Class names

KindExamplesWhere they come from
Page anatomysection wrapper section-header app-shell panelFixed by Portably, the same in every project
Project namespricing property-card booking-summary__priceChosen per project, after what the reader sees
Portably classespbly pbly-btn pbly-skip-linkThe shared foundation

Project names use the BEM pattern: a block, its elements after two underscores, modifiers after two hyphens. There are no utility classes such as mt-4 or text-muted; spacing and type live in the CSS, with tokens.

Components and pages

A component is a concept that recurs: a card, the navigation, a search form. It gets one file in css/components/. A composition that belongs to one page stays in css/pages/. Split a stylesheet when a file takes on a second responsibility, not because it got long.

Shared parts

There is no build step, so the parts every page shares (the header, the navigation, the footer) are copied into each page. Keep the copies identical: a change to one is a change to all. It keeps every page a plain HTML file that opens anywhere.

Behaviour

JavaScript lives in js/main.js and finds elements through data-js hooks, never through styling classes, so restyling can't break it. It keeps state such as aria-expanded in step with what happens.

<button type="button" data-js="menu-toggle" aria-controls="site-nav" aria-expanded="false">Menu</button>
