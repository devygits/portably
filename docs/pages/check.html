How it works

The check

One command looks at the whole project and says what's left: what to fix, what to decide and what to note.

What it looks at

Portably check · site

  ✓ Safety          nothing broken or inaccessible found
  ? Design system   2 to decide
  ✓ Structure       follows the Portably structure
  • Handoff         1 note
AreaCovers
SafetyBroken links, missing files and images, missing alt text, text that's hard to read, pages that scroll sideways, text cut off, script errors.
Design systemEvery colour, size, space, radius and shadow against the tokens; unused or unknown tokens; a complete system.
StructureThe shared files, the stylesheet order, the page anatomy and an untouched foundation.
HandoffREADME, AGENTS.md, the recorded design source and version, and files loaded from other websites.

Problems, decisions and notes

  • Problems must be fixed. fix handles the mechanical ones: values typed by hand, near misses, token fallbacks, a changed foundation file, a missing README.
  • Decisions need someone who knows the design: snap the value to a token, mark a deliberate one-off with an exception comment, or run the promote command shown.
  • Notes are worth a look before handoff, such as a design source nobody recorded. --strict counts them too.

Every finding says what happened, why it matters and what to do, with the file and line. Findings lists them all.

Safe fixes

python portably.py fix site

fix makes only changes that can't alter the design, records its snaps under "normalizations", then checks again. Anything that needs judgement is left for a person or an agent.

In a browser

With Playwright installed, check opens every page at 390px and 1440px wide. It photographs each page with the text hidden and compares every piece of text with the pixels really behind it, so text on photos, gradients and overlays is measured like text on a solid colour. It also reports pages wider than the screen (naming the element), text running past the edge, images that fail to load and script errors.

When the project defines themes (a data-theme attribute or class that points the colour roles elsewhere, or a prefers-color-scheme media query), every page is measured in each one, and a finding says which theme it's in.

Findings as data

Agents read check --json: the same findings, as data.

{
  "format": 1,
  "portably": "1.0",
  "project": "site",
  "ready": false,
  "readyStrict": false,
  "counts": {"problems": 1, "decisions": 1, "notes": 0, "fixable": 1},
  "next": "python portably.py fix site",
  "issues": [
    {
      "kind": "snap",
      "area": "system",
      "level": "problem",
      "file": "css/pages/home.css",
      "line": 25,
      "detail": "`15px` is 1px from `space.4` (16px).",
      "fixable": true,
      "decision": false,
      "command": "python portably.py fix site"
    }
  ]
}

Each finding also carries its title, snippet, other places, and the why and what-to-do text. ready is true when nothing needs fixing or deciding; readyStrict when there are no notes either.

Before handoff

python portably.py check site --strict

The strict check also fails on notes, including browser checks that didn't run. Run it last: it regenerates tokens/tokens.css, DESIGN-SYSTEM.md and DESIGN-SYSTEM.html, which belong in the handoff.

No substitutes

If the strict check can't run to the end, the project isn't finished. Report what's blocking it rather than validating the project some other way.
