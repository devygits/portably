Reference

Findings

Every finding says what happened, why it matters and what to do. These are all of them.

About this list

Every kind of finding check can report, grouped by area. The kind is what --json reports in kind; it doesn't change within a major version.

Safety

Images without a text description

missing-alt · Problem

Screen-reader users get no description, and nothing shows if the image fails to load.

What to do: Add alt="…" describing the image, or alt="" if it is purely decorative.

Links that go nowhere

broken-link · Problem

Visitors click and land on a missing page or section.

What to do: Point each link at a page that exists or an id on the page.

Missing files

missing-file · Problem

The page asks for an image, stylesheet or script that isn't in the project, so something won't show.

What to do: Add the file to the project (images go in assets/) or correct the path.

Images saved with the wrong file type

bad-image · Problem

The file's content doesn't match its extension; some browsers and servers refuse it.

What to do: Re-export the image in the format its name says, or rename it.

Pages wider than the screen

overflow · Problem

Visitors have to scroll sideways, usually on phones.

What to do: Find the element that is too wide at that screen width and let it wrap or shrink.

Text cut off at the edge of the screen

cut-off · Problem

Visitors can't read the part that's cut off, and they can't scroll to it.

What to do: Let the text wrap or shrink at that width, for example a smaller size on phones with clamp(var(--small-token), 6vw, var(--large-token)).

Images that fail to load in the browser

image-failed · Problem

Visitors see an empty space or a broken-image icon.

What to do: Check the file and its path.

JavaScript errors

script-error · Problem

Interactions on the page may stop working.

What to do: Open the page with the browser's developer console open and fix the error shown.

Text that's hard to read

low-contrast · Problem

Low-contrast text is hard or impossible to read for people with low vision, in sunlight or on a dim screen. The accessibility guideline (WCAG AA) asks for 4.5:1 for normal text and 3:1 for large text.

What to do: Make the text darker or the background lighter (or the other way round) until the ratio shown is met. On a photo, darken the overlay behind the text or give the text a solid background. If you change a colour from the design, record it under "readability" in portably.config.json.

Colour roles that are hard to read together

contrast-roles · Problem

These colours are meant to be used together, so every page that uses them inherits the problem.

What to do: Use the shade shown (or adjust one of the two colours) in tokens.json. If it changes a colour from the design, add a line to "readability" in portably.config.json, for example "color.palette.green #00915E → #008855: white button text needs 4.5:1".

Clickable elements that aren't real buttons

fake-button · Note

Keyboard users can't reach or press them unless extra code handles focus, Enter and Space.

What to do: Use a real <button>, or confirm the element handles focus, Enter and Space.

Errors in the browser console

console-error · Note

Something on the page didn't load or run as expected.

What to do: Open the page with the developer console open and read the message.

The browser checks didn't run

browser-skipped · Note

Sideways scrolling, images that fail to load, script errors and the contrast of the text on screen weren't checked.

What to do: Install Playwright (pip install playwright, then: playwright install chromium) and check again. If this machine can't run it, check with --no-browser and say so in the README.

Design system

The design system file can't be read

token-error · Problem

Without a readable tokens.json, no colour, size or spacing in the project can be checked or updated.

What to do: Correct tokens/tokens.json using the message below; the rest of the design-system check runs once it reads.

Incomplete design system

tokens · Problem

Every Portably project keeps the full set of colour roles, type sizes, spacing, radii, shadows and layout widths, so the next screen always has a value to reach for.

What to do: Restore what's missing from the Portably starter (starter/tokens/tokens.json), changing the value if the design needs a different one.

Values typed by hand that already exist as tokens

token-value · Problem

They look right today but won't follow when the token changes.

What to do: Use the token instead. fix does this for you.

Values almost the same as a token

snap · Problem

Near-identical values, like 15px next to a 16px step, are usually slips, and they make the design drift.

What to do: Snap them to the token. fix does this for you and records each one in DESIGN-SYSTEM.md.

Token values repeated as fallbacks

fallback · Problem

var(--token, 8px) keeps a second copy of the value, which goes stale when the token changes.

What to do: Keep only the token. fix removes the copy.

A changed base text size

root-size · Problem

Portably's sizes assume the browser's 16px base. Changing it quietly rescales every token, so the system no longer means what it says (a 1440px width becomes 1530px).

What to do: Remove it and put the design's real sizes in tokens.json (its body size in font.size.base).

Design values kept outside tokens.json

hidden-token · Problem

A second, hidden set of values means tokens.json is no longer the one place the design lives.

What to do: Move the value into tokens.json, then point the variable at the token.

References to tokens that don't exist

unknown-variable · Problem

The browser ignores them, so the style silently disappears.

What to do: Correct the name, or add the token to tokens.json.

Tokens you added but never use

unused-token · Problem

An unused token usually means the design moved on, or something was built without it.

What to do: Use it where the design needs it, or delete it from tokens.json.

Repeated values that aren't in the system yet

promote · Decision

A value used in several places is a design decision. Recording it once keeps every use in sync.

What to do: If it's intentional, add it to the system with the command shown. If it's drift, change each place to an existing token.

One-off values outside the system

off-system · Decision

Portably can't tell whether each one is a deliberate choice or drift.

What to do: Deliberate: add /* exception: reason */ at the end of the line. Drift: use the closest token.

Shadows written by hand

shadow · Decision

Hand-written shadows drift apart from each other over time.

What to do: Use shadow.sm, shadow.md or shadow.lg, add a repeated one with the command shown, or mark a deliberate one-off with /* exception: reason */.

Screen widths outside the project's breakpoints

breakpoint · Decision

Layouts that change at many slightly different widths are hard to test and maintain.

What to do: Use a project breakpoint, add a repeated one with the command shown, or mark a one-off with /* exception: reason */ on the @media line.

Exception comments that are no longer needed

stale-exception · Note

The value now follows the system, so the comment only adds noise to the exception list.

What to do: Remove the comment. fix does this for you.

Structure

Missing project files

missing-path · Problem

Every Portably project has the same files, so anyone can find their way around.

What to do: Restore them. A fresh python portably.py init folder has a copy of each one to take from.

Portably foundation files that were changed or are missing

foundation-changed · Problem

foundation/ is shared Portably code (reset, button, skip link). Changes there are hard to find and get lost on update.

What to do: fix restores the originals. Put project styles in css/ instead.

Stylesheets out of the Portably order

css-entry · Problem

The order decides which rules win; a different order makes styles behave differently in each project.

What to do: Keep css/project.css importing base.css, layout.css, components.css and pages.css, in that order.

Cascade layers in project CSS

css-layer · Problem

Project styles must stay outside @layer so they reliably override the foundation.

What to do: Remove the @layer wrapper from the file.

Pages not set up the Portably way

page-setup · Problem

Without the namespace class on <body> and the three stylesheets in order, tokens and foundation styles don't apply.

What to do: Give <body> the class shown and load foundation/system.css, tokens/tokens.css and css/project.css, in that order.

Sections outside the page anatomy

anatomy · Note

Every Portably page uses section > wrapper, so spacing and widths stay consistent and the markup looks familiar.

What to do: Give each <section> in <main> the section class and put its content in <div class="wrapper">. App screens use app-shell instead.

Inline styles

inline-style · Note

Styles inside the HTML are easy to miss when the design changes.

What to do: Move them into a stylesheet in css/ unless JavaScript sets them.

Portably's own source is out of sync

framework · Problem

The starter, foundation and docs must agree for new projects to start correctly.

What to do: Fix the file named below.

Handoff

Missing README.md or AGENTS.md

handoff-file · Problem

README.md tells the next person what was built and what's missing; AGENTS.md tells the next person or AI agent how to work on the project and check it.

What to do: fix creates them from the Portably templates. Fill in the README's pages and known gaps.

Design notes that can't be read

context-format · Problem

DESIGN-SYSTEM.md lists them for the next person; in another shape they are lost.

What to do: In portably.config.json, write "source" as a sentence, and "assumptions", "deviations", "normalizations" and "readability" as lists of sentences.

The design source isn't recorded

source · Note

Without it, the next person or AI agent can't compare the implementation with what it was built from.

What to do: Add "source" to portably.config.json: where the design came from (a Figma file and its frames, screenshots, a website, a brief) and when.

A different or unrecorded Portably version

version · Note

Portably's rules only change between major versions; the version tells the next person which ones the project follows.

What to do: Read the CHANGELOG entries marked Breaking since the project's version, check again, then set "portably" in portably.config.json to the version shown.

Files loaded from other websites

remote · Note

The project breaks if that site changes or goes offline, and the files may need a licence.

What to do: Download them into assets/ where you can; otherwise list them in the README.

Paths that start with /

host-root · Note

They only work when the site sits at the root of a domain, so they can't be checked here.

What to do: Use relative paths (assets/logo.svg) unless the host needs /.
