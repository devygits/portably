Moving to another stack

A Portably project runs without Portably, and it is organised so it can move to a framework later without starting over.

What carries over

  • The design system. tokens.json uses the design-tokens (DTCG) format that design tools and token tools read. tokens.css is plain CSS custom properties that any stack can load.
  • The components. Each file in css/components/ is one component, and DESIGN-SYSTEM.md lists the classes it styles and the pages that use it: a ready component map.
  • The names. Class names say what things are, so they stay meaningful as component names.
  • The decisions. The source, assumptions and deviations travel with the tokens.

How to move

Load foundation/system.css and tokens/tokens.css in the new stack, turn each component file into a component that keeps its class names, and move each page's composition into the page or route. The design moves with the names and tokens.

// React: the pricing-card component keeps its classes and tokens
export function PricingCard({ plan }) {
  return (
    <article className="pricing-card">
      <h3 className="pricing-card__name">{plan.name}</h3>
      <p className="pricing-card__price">{plan.price}</p>
    </article>
  );
}

Living inside another site

Portably's own names share one prefix, the namespace: pbly by default. It keeps them clear of the site or application a project ends up inside. Choose another one when the project starts:

python portably.py init site --namespace acme

That gives .acme, acme-btn and --acme-color-action-primary. Token paths don't change. Project classes never use the namespace. Portably's rules only apply inside the scope, and its reset and tokens sit in low-precedence cascade layers, so host styles can override them. This reduces collisions; it doesn't isolate the project. Use an iframe or Shadow DOM when you need hard isolation.
