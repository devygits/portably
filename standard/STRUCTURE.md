# Structure contract

Every Portably project has the same files, the same page skeleton and the same three kinds of class name. A developer or agent who opens any Portably project recognizes the structure immediately; everything inside it uses readable project names, so a page is understandable from its HTML without knowing Portably.

## Project files

```text
project/
├── index.html
├── pages/                 more pages, only when the design has them
├── foundation/            Portably's shared CSS; never edited
├── tokens/
│   ├── tokens.json        the design system
│   └── tokens.css         generated by `check`
├── css/
│   ├── project.css        imports base, layout, components, pages, in that order
│   ├── base.css           project-wide element defaults
│   ├── layout.css         the page anatomy and layouts reused across sections
│   ├── components.css     imports css/components/*.css
│   ├── components/        one recurring interface concept per file
│   ├── pages.css          imports css/pages/*.css
│   └── pages/             compositions that belong to one page
├── js/main.js             behaviour, on data-js hooks
├── assets/                images, icons, fonts
├── AGENTS.md              how to work on the project, for people and AI agents
├── DESIGN-SYSTEM.md       generated by `check`
├── DESIGN-SYSTEM.html     generated by `check`: the system drawn with its tokens
├── portably.config.json   Portably version, namespace, design context and decisions
└── README.md              pages, remote dependencies, known gaps
```

Every page loads `foundation/system.css`, `tokens/tokens.css` and `css/project.css`, in that order, and has the namespace class (`pbly`) on `<body>`. Project CSS stays outside `@layer` so it reliably overrides the foundation. Split a stylesheet when a file acquires a distinct responsibility, not because it got long.

## Class names

Every class belongs to one of three vocabularies:

| Vocabulary | Names | Where they come from |
| --- | --- | --- |
| **Page anatomy** | `section`, `wrapper`, `section-header`, `eyebrow`, `app-shell`, `panel` and their parts | fixed by Portably, the same in every project (below) |
| **Project names** | `pricing`, `property-card`, `booking-summary__price` | chosen per project, BEM-style, after what the reader sees |
| **Portably public classes** | `pbly` (the opt-in scope), `pbly-btn` and its modifiers, `pbly-skip-link` | the shared foundation |

There are no layout, spacing or typography helper classes. Relationships between elements are written in project CSS with tokens. Project classes never use the reserved namespace: `property-card__price`, not `pbly-property-card__price`. Add a wrapper only when it has a job: it sets a width, creates a layout context or groups a meaningful part.

HTML semantics come first: a section is a `<section>`, an action is a `<button>`, navigation is `<nav>`, whatever the classes. Buttons styled with `pbly-btn` stay buttons, and links stay links.

## Page anatomy

The roles are defined in the starter's `css/layout.css`. Their values come from tokens, so the design changes how they look, never what they are called.

### Site pages

```text
site header
main
 └─ section                  padding above and below each page section
     └─ wrapper              content width and side gutters
         ├─ section header   eyebrow, title and intro (optional)
         └─ content          project components, grids and page compositions
site footer
```

```html
<main id="main">
  <section class="section pricing">
    <div class="wrapper">
      <header class="section-header">
        <p class="eyebrow">Pricing</p>
        <h2 class="section-header__title">Plans for every team</h2>
        <p class="section-header__intro">Start free and upgrade when you need to.</p>
      </header>
      <div class="pricing__plans">…</div>
    </div>
  </section>
</main>
```

| Class | Role | Values from |
| --- | --- | --- |
| `section` | a page section; pads its content above and below | `layout.section.padding` |
| `wrapper` | limits content to the page width and adds side gutters | `layout.wrapper.max`, `layout.wrapper.gutter` |
| `wrapper--narrow` | a narrower wrapper for reading-focused content | `layout.wrapper.narrow` |
| `section-header` | the heading group at the top of a section | spacing and text tokens |
| `section-header__title`, `section-header__intro` | its title and introduction; the eyebrow uses `eyebrow` | text tokens |

Rules:

1. Every `<section>` directly inside `<main>` has the `section` class and one `wrapper` inside it. A section with a full-bleed background keeps the background on the section and the content inside the wrapper.
2. The site header and footer use `wrapper` for their content width too: `<div class="wrapper site-header__inner">`.
3. Add the section's own name next to the role: `class="section pricing"`. Section-specific styling goes on the project name (`.pricing`), in `css/pages/` or `css/components/`.
4. The padding sits inside each section, so a section with its own background colour keeps the space inside that colour. Two plain sections next to each other are **twice** the padding apart: if the design says sections are 72px apart, set `layout.section.padding` to 36px.
5. A section whose design needs different spacing overrides it on its project name, using a token or a logged exception.
6. Use `section-header` for the heading group whenever a section has one. Do not invent `section-title`, `heading-block` or similar.

### App screens

Dashboards, admin tools and other application screens use the app shell instead of stacked sections.

```text
app shell
 ├─ sidebar      navigation (optional)
 ├─ top bar      search, account, actions (optional)
 └─ main
     └─ panel    a region: stats, a chart, a table, a form
```

```html
<body class="pbly">
  <div class="app-shell">
    <nav class="app-shell__sidebar" aria-label="Primary">…</nav>
    <header class="app-shell__topbar">…</header>
    <main class="app-shell__main" id="main">
      <section class="panel sales-summary">…</section>
      <section class="panel listings-table">…</section>
    </main>
  </div>
</body>
```

| Class | Role | Values from |
| --- | --- | --- |
| `app-shell` | the screen grid: sidebar beside top bar and main | `layout.sidebar.width` |
| `app-shell__sidebar`, `app-shell__topbar`, `app-shell__main` | the shell's regions | spacing tokens |
| `panel` | one region inside the main area | spacing, radius and surface tokens |

Rules:

1. Arrange panels with project CSS on the main area or a project class (`.overview__grid`). The shell does not decide panel columns.
2. Below the medium breakpoint the shell stacks: top bar, sidebar, main. Collapsing the sidebar behind a menu button is project behaviour, with a `data-js` hook.
3. A project without app screens deletes the app-shell block from `layout.css`.

### Other layouts

A page that is neither stacked sections nor an application screen, such as documentation with a sidebar, an article and a list of contents, keeps `wrapper` for its width and defines its layout in `css/layout.css` under a project name (`docs-layout`, with its regions as elements: `docs-layout__main`). The project records it under "This project's conventions" in its `AGENTS.md`. Portably's own documentation site is built this way.

### Shared parts

There is no build step, so parts every page shares (the site header, the navigation, the footer) are copied into each page. The copies stay identical; a change to one is a change to all.

## What stays project-owned

Everything inside a wrapper or panel: components, grids, cards, page compositions and their names. Portably fixes the skeleton, not the content.

## Checks

`python portably.py check` adds a Structure note when a `<section>` directly inside `<main>` lacks the `section` class or a `wrapper`. Pages that use `app-shell` are checked as app screens instead. `check --strict` treats these notes as problems.
